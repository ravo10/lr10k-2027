## Where to start reading

The four parts and their main files:

| Part | Start with | Then |
|---|---|---|
| Hardware I/O (LR 10K, serial port) | LR10KMachine (handshake, sequences, readings) | LR10KProtocol, SerialReader, Win32SerialPort, LR10KStatus |
| Calculations | TestCalc.h (`CalculateTensile`, `CalculateBending3Point`) | MaterialCalc.h, LR10KMeasurement.h, LoadSafety.h |
| GUI | appstructs.cpp (windows), main.cpp (main loop, DirectX 12) | TabSystem.cpp (tabs and test data), Calculator.cpp, styles.h |
| Excel export | ExcelReport.h (what goes in the book, no I/O) | ExcelWriter (libxlsxwriter), ExcelExport.cpp (from a tab) |

Files whose header says *Portable ... and unit tested* contain no Windows, ImGui or OpenCV code. Each has a test in `tests/`, which runs on every push (*Actions* > *Tests*). New logic should go in a header like that whenever possible, so it can be tested without the machine.

## How a reading gets to the graph

1. **Serial thread** (SerialReader): reads bytes from the COM port into a RingBuffer.
2. **Interpreter thread** (LR10KMachine): splits the bytes into messages (LR10KProtocol) and turns them into LR10KReadings (load, extension, status).
3. **GUI thread** (main loop in main.cpp, once per frame):
   - adds the readings to the running test's tab;
   - runs `LR10KControlSystem::LoadSafetyTick()` (the 50 N blocker and the load limit, see LoadSafety);
   - draws the windows; `AppConsole::FlushPending()` adds console lines written by other threads.
4. **When a test ends:** the Calculator turns the tab's data into results (TestCalc), and the Excel export builds an ExcelReport::Report from the tab and saves it (ExcelWriter).

## Threads

| Thread | Started by | Touches |
|---|---|---|
| GUI (main) | `main()` | Everything in ImGui, the tabs, the settings |
| Serial reader | SerialReader | The ring buffer only |
| Interpreter | LR10KMachine | Readings and status, through callbacks and LR10KStatus |
| Connect / send setup / reconnect | `LR10KDataDeEncryptionSystem` (one at a time) | The machine and LR10KStatus |
| Extensometer camera | `ExtensiometerWorkerThread` in appstructs.cpp | Atomics in `AppExtensiometer`; the recording paths under `recording_mutex` |

Rules learned the hard way:

- Do not share a `std::string` or a pointer to a tab between threads. Use atomics, LR10KStatus (mutex inside) or a mutex. The camera thread used to keep a pointer to a tab that could be closed.
- Do not call ImGui from any thread except the GUI thread. Other threads write to the console through `AppConsole`, which queues the lines.
- Nothing that writes a file (settings, logs) should run every frame. Save when a value changes, or when a slider is let go (`ImGui::IsItemDeactivatedAfterEdit()`).

## Conventions

- **Settings file:** JSON in `%AppData%`, named `v<LR10KSettingsFileVersion>_lr10k.ini` (FileSystem.cpp). A missing *required* key resets all settings, so new keys must be read as optional with a default. Change `LR10KSettingsFileVersion` only when the old file cannot be used any more.
- **Version:** `LR10KAppVersion` in common.h. It is shown in *About* and on this page. Also change `vcpkg.json`, and the installer's *ProductVersion* in Visual Studio.
- **ImGui IDs:** use `"Visible text###StableId"` when a label changes (language, unit, state), so the window, tab or table keeps its position and settings.
- **Comments:** Doxygen style (`@brief`, `@param`, `@details`, `//!<`). The *Docs* workflow lists the warnings in its run summary; a wrong `@param` name shows up there.

## Recipes

**Add a value to the Excel report:** add it to ExcelReport::Report, fill it in `MakeExcelReport()` (ExcelExport.cpp), put it in a section in `ReportSections()` (ExcelReport.h), and add a check to `tests/excel_report_test.cpp`. The *excel-files* CI job writes sample books (artifact *excel-sample-reports*) so the result can be opened without the lab PC.

**Add a setting:** write it in the save function in FileSystem.cpp and read it with `settings.contains(...)` (optional), so older settings files still load.

**Add a unit test:** copy a small test such as `tests/load_safety_test.cpp`, and add a step to `.github/workflows/tests.yml`. The tests are built with `g++` and a sanitizer (AddressSanitizer + UBSan, or ThreadSanitizer for code with threads), so out-of-bounds reads and data races fail the test.

**Test the serial code without the machine:** `tests/connect_replay_test.cpp` plays a recorded LR 10K session (`tests/data/*.log`) through a fake serial port. Record a new log with *Log serial traffic to file* (under *Troubleshooting* in the menu), started before *Connect PC*.
